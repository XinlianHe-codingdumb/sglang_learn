SGLang Source Field Guide

A guided tour of the SGLang runtime (python/sglang/srt) for someone who has read the paper and run a model, but has not opened the code yet. It follows one request from HTTP to GPU and back. Then it goes deep on three areas: KV cache, prefill/decode disaggregation, and the decoding step where entropy signals live.

Every file reference links to the exact line on GitHub at commit 3420bae (main, 16 Oct 2026). SGLang moves fast, so line numbers drift on newer commits, but the class and function names are stable anchors. Search for them.

00

Start here

The repo has about 10,700 files. You need roughly 25 of them to understand how serving works.

Reading order

Read chapters 01 → 02 first. They give you the vocabulary (Req, ScheduleBatch, ForwardBatch, prefill vs decode) that everything else uses. After that, chapters 03–05 (KV cache), 06 (PD) and 07–08 (decoding) are independent. Read them in any order.

The directories that matter

All paths are under python/sglang/srt/ unless noted. Orange cards are the three focus areas.

entrypoints/

HTTP server (FastAPI), OpenAI-compatible routes, the Engine that spawns all processes.

managers/

The control plane: TokenizerManager, Scheduler, DetokenizerManager, batch and request structs, scheduling policy.

model_executor/

ModelRunner: turns a batch into GPU tensors, runs the model or a CUDA graph, samples.

layers/

Building blocks: RadixAttention, attention backends (FlashInfer, FA3, Triton, TRT-LLM), the Sampler, logits processor, MoE.

mem_cache/

All KV memory: token pools, slot allocators, radix trees, host (L2) mirrors, storage (L3) backends.

disaggregation/

PD split: prefill and decode scheduler mixins, transfer backends (Mooncake, NIXL, MORI, Ascend).

speculative/ · sampling/

EAGLE/NGRAM/DSPARK speculative decoding, sampling params, penalties, custom logit processors.

models/

One file per architecture (Llama, Qwen, DeepSeek…). Mostly standard PyTorch modules wired to SGLang layers.

arg_groups/fields/

Every CLI flag, grouped (memory.py, disagg.py, spec.py, schedule.py) with help text and defaults.

sgl-model-gateway/ (repo root)

The router (Rust) that sits in front of many workers and pairs prefill with decode servers.

Tip. When a flag name puzzles you, search for it in arg_groups/fields/. The help strings there are the most up-to-date description of what each knob does.
01

A request's journey

SGLang is several OS processes connected by ZeroMQ sockets. Know which process owns which job and the rest of the code becomes easy to place.

Follow one /generate callStep through

The three data structures to keep apart

StructLives inWhat it holds
ReqScheduler (CPU)One request: input ids, output ids so far, sampling params, its row in the KV pool, the radix-tree node it locked, finish state.
ScheduleBatchScheduler (CPU)A list of Reqs plus a forward_mode. Owns pool references and does the allocation (prepare_for_extend / prepare_for_decode).
ForwardBatchModelRunner (GPU)Flat GPU tensors: input_ids, positions, seq_lens, req_pool_indices, out_cache_loc (where new KV gets written). Built by ForwardBatch.init_new.

The module docstring at the top of schedule_batch.py states this split. The reason it matters: the scheduler does bookkeeping on Python lists, the runner only sees tensors, and the overlap scheduler (chapter 02) depends on the two being separable.

Forward modes

ForwardMode tells the attention backend what shape of work it is doing. You will meet these constantly:

ModeMeaning
EXTENDPrefill. "Extend" because the first part of the sequence may already be cached (prefix hit), so only the remainder is computed.
DECODEOne new token per request.
MIXEDChunked prefill and decode rows in one forward (--enable-mixed-chunk).
TARGET_VERIFY / DRAFT_EXTEND_V2Speculative decoding: the target model checks draft tokens; the draft model catches up.
PREBUILTPD decode server: the KV arrived over the network, so prefill is skipped and only metadata is set up.
IDLEData-parallel attention: this rank has no work but must join collective ops.
Why is tokenization in a separate process from scheduling?

The scheduler loop is latency-critical: every millisecond it spends on CPU work is a millisecond the GPU may sit idle between batches. Tokenizing long prompts and detokenizing streams are CPU-heavy and would stall it. Python's GIL means threads would not help much, so they run in other processes and talk over ZMQ.

02

The scheduler loop

managers/scheduler.py is 6,000+ lines, but its heart is a while True loop of about 30 lines. Everything else is a helper for one of its four steps.

Which loop actually runs

_dispatch_event_loop_once picks one of nine loops from two settings. The PD loops (chapter 06) are the same four steps with extra queues bolted on.

Overlap scheduling: hide the CPU

In the normal loop the GPU waits while the CPU processes results and builds the next batch. event_loop_overlap launches batch N+1 before processing batch N's result. Results go into a result_queue and are popped one iteration later. The GPU kernels are asynchronous, so the CPU's bookkeeping for N overlaps with the GPU computing N+1.

Timeline, normal vs overlapDiagram

Caveat: batch N+1 is built before N's sampled token is known. The code copes with this using placeholder tokens resolved on the GPU (a "future map", see managers/overlap_utils.py). It also has is_disable_overlap_for_batch for cases where it must sync, for example when grammar-constrained decoding needs the previous token.

Picking the next batch

get_next_batch_to_run follows a simple rule: prefill wins. It first merges the last prefill batch's requests into running_batch (they are decoding now). Then it tries to build a new prefill batch from waiting_queue. Only if that yields nothing does it run one decode step for running_batch.

  1. Sort the waiting queue with the schedule policy (SchedulePolicy.calc_priority). The default lpm (longest prefix match) runs requests with the biggest cache hits first, because they are cheapest.
  2. Admit requests one by one with a PrefillAdder (add_one_req). Each request first does a radix-tree prefix match (req.init_next_round_input(tree_cache)). Then the adder checks three budgets: total free KV tokens (counting what eviction could free), max_prefill_tokens (default 16384) for this forward, and chunked_prefill_size.
  3. Chunk long prompts. If a prompt does not fit the chunk budget, the adder takes a slice and marks it chunked_req. The next iteration continues it. This bounds how long any prefill forward takes, so decode requests aren't starved.
  4. Build the batch: ScheduleBatch.init_new(...) then prepare_for_extend(), which allocates KV slots for the new tokens.

When decode runs out of memory: retraction

Admission is optimistic. It reserves room for future output tokens using new_token_ratio, a guess at what fraction of max_new_tokens a request will really use. If the guess is wrong, update_running_batch finds check_decode_mem() fails. It then calls batch.retract_decode(): some running requests are evicted back to the waiting queue (their KV freed), and new_token_ratio is raised so admission becomes more conservative. The ratio then decays slowly back down each step. The log line to look for is #retracted_reqs.

A long prompt (40k tokens) arrives while 100 requests are decoding. With chunked_prefill_size=8192, what happens?

The prompt is split into 5 chunks. Each loop iteration runs one chunk as a prefill batch (prefill wins). With --enable-mixed-chunk, the decode rows ride along in the same forward as MIXED. Without it, they wait for the next decode step. Either way, no single forward is a 40k-token monster that freezes everyone's token stream for seconds.

03

KV memory: three layers of indirection

The KV cache is not one tensor per request. It is one big pool per layer, and two index tables say which slots belong to whom. That indirection is what makes prefix sharing, paging, and PD transfer possible.

LayerClassShape / content
Request → token slotsReqToTokenPoolreq_to_token: int32 [max_running_reqs+1, max_context_len]. Row = req.req_pool_idx; entry j = slot index holding token j's KV.
Free-slot bookkeepingTokenToKVPoolAllocator / PagedTokenToKVPoolAllocatorA tensor free_pages. alloc(n) slices off the front; free(idx) appends. With page_size>1 it hands out whole pages.
Physical bytesMHATokenToKVPool (also MLATokenToKVPool for DeepSeek)k_buffer[layer], v_buffer[layer]: [size+page_size, kv_heads, head_dim], one pair per layer.

Slot 0 is reserved as a dummy. CUDA-graph padding rows write their garbage there, which is why free slots start at 1.

Who writes and who reads

Write. During a forward, every attention layer is a RadixAttention. It calls the backend, which calls token_to_kv_pool.set_kv_buffer(layer, out_cache_loc, k, v). out_cache_loc is the list of freshly allocated slots for this batch's new tokens.

Read. The attention kernel needs, for each request, the list of slots holding its context. The backend builds a flat kv_indices array by gathering rows of req_to_token on the GPU (create_flashinfer_kv_indices_triton). That array, plus kv_indptr offsets, is exactly the "page table" format FlashInfer and FlashAttention's paged mode accept.

How big is the pool?

At startup, after loading weights, the runner measures free GPU memory, keeps --mem-fraction-static of the total for weights + KV, and divides the KV share by bytes-per-token. For an MHA model that is 2 × layers × kv_heads × head_dim × dtype_bytes. The server log prints the result as max_total_num_tokens, the most useful number to know about your deployment.

Your 3B model has 36 layers, 2 KV heads, head_dim 128, bf16. How many bytes per token of KV?

2 (K and V) × 36 × 2 × 128 × 2 bytes = 36,864 bytes ≈ 36 KiB per token. With 20 GiB left for KV, that is about 580k tokens. Check your own model's config.json for the real values.

04

Radix cache: reusing prefixes

RadixAttention, the core idea of the SGLang paper, is a radix tree whose edges are token sequences and whose values are the KV slot indices for those tokens.

Two classes to know. RadixCache in radix_cache.py is the classic, compact implementation (about 800 lines). Read it to learn the algorithm. UnifiedRadixCache is what default_radix_cache_factory builds by default today. It runs the same algorithm, but each node carries per-component data (Full attention, sliding-window, Mamba state) plus HiCache host copies. Learn on the first, debug on the second.

The four operations

OperationWhen the scheduler calls itWhat it does
match_prefixAdmitting a request (init_next_round_input)Walks down matching tokens. If the match ends mid-edge, it splits the node (_split_node) so the boundary is exact. Returns the concatenated slot indices, which become req.prefix_indices.
inc_lock_ref / dec_lock_refAdmit / releaseWalks from the node to the root, incrementing lock_ref. Moves token counts between evictable_size_ and protected_size_.
insertRequest finishes or a chunk completes (checkpoint)Walks the shared part. The unshared tail becomes a new leaf whose value is the request's own slots, so ownership passes from the request to the tree.
evictAllocator is short of slotsHeap of unlocked leaves ordered by the eviction strategy (LRU by default). Frees a leaf's slots, deletes it, and pushes the parent if it became a leaf.

Things to try. Send the two "chat" presets: the second hits the shared system prompt and splits a node. Send several requests without finishing them, then try a new one: eviction cannot touch locked paths, so the request is refused. In the real scheduler it would wait in the queue, or running requests would be retracted.

The lifecycle inside the scheduler

  1. Admit: match_kv_cache sets req.prefix_len and req.last_node, and the matched path is locked. KV slots are allocated only for extend_input_len = len(input) − prefix_len.
  2. Chunk done: checkpoint_kv_cache inserts the computed part, so a second request with the same long document can hit it before the first finishes.
  3. Finish: release_kv_cache inserts (checkpoint), frees slots the tree already had (duplicates), unlocks, and frees the request's req_to_token row.
Eviction policies. --radix-eviction-policy accepts lru (default), lfu, slru, priority, tlru and more. All live in evict_policy.py as tiny classes with one method, get_priority(node). That makes a new eviction idea a very cheap experiment.
Why must a split happen during match, not only during insert?

The request will lock the matched path. If the match ended in the middle of an edge, the node would hold both shared tokens (that the request uses) and unshared tokens (that it does not). Locking it would protect the unshared part from eviction for no reason, and the slot list would be the wrong length. Splitting makes the locked unit exactly what the request depends on.

05

HiCache: GPU → host → storage

GPU memory holds maybe a few hundred thousand tokens. Multi-turn chat and agent workloads revisit far more context than that. HiCache adds two slower but larger tiers under the radix tree.

TierWhereCodeSize knob
L1GPU HBMmem_cache/memory_pool.py--mem-fraction-static
L2Pinned host DRAMmem_cache/memory_pool_host.py, pool_host/--hicache-ratio (host/device size, default 2.0) or --hicache-size GB
L3Distributed / disk storagemem_cache/storage/<backend>/--hicache-storage-backend: file, mooncake, hf3fs, nixl, aibrix…

Turn it on with --enable-hierarchical-cache. The data movement is run by HiCacheController on separate CUDA streams and threads, so copies overlap compute. The tree nodes gain host_value next to value. A node can be on GPU, on host, or both.

Write policy (--hicache-write-policy)

  • write_through (default): copy to host as soon as a node is cached. Eviction from GPU is then free, because the host copy already exists.
  • write_back: copy to host only when evicting from GPU. Less PCIe traffic, but slower evictions.
  • write_through_selective: write through only nodes that have been hit often enough to be worth it.

Load path

When a match ends at a node whose KV is on host only, the request carries host_hit_length. During admission, PrefillAdder.add_one_req calls tree_cache.init_load_back(...) to allocate GPU slots and queue an H2D copy. A LayerDoneCounter lets the forward start on layer 0 while later layers are still loading. For L3, prefetch_from_storage starts fetching when the request arrives. --hicache-storage-prefetch-policy (best_effort / wait_complete / timeout) decides how long a request waits for it.

Connects to PD. Mooncake appears twice in this codebase: as an L3 HiCache store (mem_cache/storage/mooncake_store/) and as a PD transfer engine (disaggregation/mooncake/). Same RDMA library, two different jobs.
06

PD disaggregation

Prefill is compute-bound: one big matmul over thousands of tokens. Decode is memory-bandwidth-bound: tiny matmuls, a huge KV read per step. On one GPU they interfere. A long prefill stalls every decode stream, which is the TTFT-versus-ITL tradeoff. PD puts them on separate servers and ships the KV cache between them.

One request through a PD deploymentStep through

The handshake key: bootstrap_room

The router sends the same request to both servers at once, adding bootstrap_host, bootstrap_port and a random 63-bit bootstrap_room. The room id is how a prefill-side KVSender and a decode-side KVReceiver, created independently on two machines, find each other.

Transfer states

Both sides poll a small state machine, KVPoll: Bootstrapping → WaitingForInput → Transferring → Success, or Failed. In tensor parallelism every rank must agree, so the polls are all-reduced across the TP group (poll_and_all_reduce_attn_cp_tp_group) before anyone acts on them.

How the bytes move

At startup each side registers its KV buffer addresses (KVArgs.kv_data_ptrs, one pointer per layer) with the transfer engine. When a chunk is ready, the prefill side knows its own slot indices and the decode side's pre-allocated slot indices. Copying is pure pointer arithmetic: for each layer, for each run of contiguous pages, src = base + idx × item_len. The engine writes these blocks directly into the decode GPU's memory with one-sided RDMA.

Besides KV, the last chunk carries a small metadata buffer (MetadataBuffers). It holds the first output token (prefill already sampled it), logprobs, cached-token count, and the hidden states that EAGLE's draft model needs to keep going on the decode side.

Why does decode pre-allocate KV before prefill even starts computing?

RDMA is a one-sided write into a known address. Prefill can only send a chunk once it knows the destination slots. Pre-allocating early also gives backpressure: if decode is full, the request waits in decode's PreallocQueue, and prefill's bootstrap never completes. So prefill does not waste compute on KV that has nowhere to go. The --disaggregation-decode-allocation-policy prefill_complete option flips this to reserve later, trading backpressure for decode memory efficiency.

07

Sampling and speculative decoding

The model produces logits. Everything between logits and the next token id is where decoding-side research plugs in: sampling, constraints, speculation, and entropy.

The sampling path

ModelRunner.sample first applies logit bias and grammar masks (sampling_info.apply_logits_bias, penalties). Then it calls Sampler.forward:

  1. All requests greedy? Take torch.argmax(logits, -1) and stop.
  2. Otherwise, divide by per-request temperatures, softmax into probs.
  3. Apply top-k / top-p / min-p and sample. Fused FlashInfer kernels are used where possible, with top_k_top_p_min_p_sampling_from_probs_torch as the reference.
  4. If logprobs were requested, compute them from the same probs and store them on logits_output.

All per-request knobs are packed into one GPU-side struct, SamplingBatchInfo (sampling/sampling_batch_info.py), so the whole batch samples in one kernel even when every request has different settings.

Speculative decoding, EAGLE style

Decode is bandwidth-bound: reading the weights once costs about the same whether you verify 1 token or 8. So a small draft model guesses several tokens, and the big target model checks them all in one forward. EAGLEWorkerV2.forward_batch_generation has three phases per decode step:

PhaseModelWhat happens
draftdraftspeculative_num_steps autoregressive steps, keeping top speculative_eagle_topk per step. The result is a token tree of speculative_num_draft_tokens nodes.
verifytargetOne TARGET_VERIFY forward over all tree nodes with a tree attention mask. Greedy: verify_tree_greedy keeps the longest path where draft equals target argmax. Sampling: tree_speculative_sampling_target_only.
draft_extenddraftThe draft model consumes the accepted tokens and the target's hidden states, ready for the next round.

Rejected draft tokens' KV slots are freed; accepted ones are moved into place (move_accept_tokens_to_target_kvcache). The key metric is accept length, the average tokens gained per verify, shown as accept len in the server log.

Two existing knobs are relevant if you think about confidence-driven decoding:

  • --speculative-accept-threshold-single and --speculative-accept-threshold-acc (both default 1.0) relax acceptance. A draft token is accepted if its target probability exceeds a threshold, or its acceptance probability is boosted to min(1, p / threshold_acc). This trades exactness for speed.
  • adaptive_spec_params.py changes speculative_num_steps at runtime from observed accept lengths and batch size. For example, at batch size 1 it picks from steps [1, 3, 5, 7]; at 64 it uses 0. It is a feedback controller over a crude confidence signal.
08

Entropy in the decoder

Entropy of the next-token distribution, H = −Σ p·log p, measures how unsure the model is. Low entropy means one token dominates: easy to draft, easy to accept, safe to skip work. High entropy means the opposite.

Entropy in bits. Order matches SGLang: temperature, softmax, then top-k / top-p truncation and renormalization. "H kept" is the entropy of the distribution actually sampled from.

What already exists in the code

1. Entropy-bounded parallel decoding (diffusion LLMs)

SGLang serves diffusion LLMs (srt/dllm/). These denoise a whole block of tokens at once. In gemma4_renoise.py, each step computes the per-position entropy, sorts positions from most to least certain, and commits positions while their cumulative entropy stays under entropy_bound (default 0.1). The rest get re-noised for another pass. A block stops early when its mean entropy drops below confidence_threshold.

2. A return_entropy field that is not wired up

GenerateReqInput has return_entropy: bool = False (io_struct.py:335), and the output structs carry output_token_entropy_val. But the scheduler's output streamer currently fills it with None (output_streamer.py:756). The plumbing from API to detokenizer exists; the computation in the sampler does not. Implementing it is a contained first project that touches sampler → batch result → streamer.

3. Confidence-ordered drafting (DSPARK)

The DSPARK speculative algorithm (speculative/dspark_components/) has a draft model with a confidence head (dspark_draft.py). It uses the confidence to decide how many draft tokens per request are worth verifying. This is the closest existing relative of an "entropy-adaptive speculation" design.
